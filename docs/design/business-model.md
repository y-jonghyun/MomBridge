## 20. 수수료율: 표시 문구 "수수료 10%" ↔ 사업계획 "체험단원 60 : 플랫폼 40"

### 현재 코드 (사실)
| 위치 | 내용 |
|---|---|
| `backend/src/modules/submissions/submissions.routes.ts:212` | 콘텐츠 승인 시 정산 생성: `fee = rewardAmount * 0.1`, `netAmount = rewardAmount - fee` — **10% 하드코딩** |
| `frontend/src/app/missions/[id]/page.tsx:153` | "(수수료 10% 제외 후 지급)" — **고정 문구**, 계산과 연결되지 않음 |
| `backend/src/modules/missions/missions.schema.ts` `expectedMissionAmount` | 고객사 결제액 = **1인 보상 × 모집 인원**. 고객사는 보상만 내고, 플랫폼 수익은 체험단원 보상에서 떼는 10%뿐 |
| 체험단원 화면(`participant/page.tsx`)·운영자 정산 표 | 저장된 `platformFee`·`netAmount`를 그대로 표시 |

추가로 발견한 문제
- 소수 계산: `33,333원 × 0.1 = 3,333.3원`처럼 원 단위 아래가 생긴다(DB는 소수 2자리까지 저장). 원화는 원 단위로 내림·반올림 규칙을 정해야 한다.
- 수수료율이 바뀌면 이미 모집 중인 미션에도 새 비율이 적용된다(승인 시점에 계산하므로).

### 사업계획 60:40과의 관계
현재 구조로는 플랫폼 몫이 10%다. 60:40을 맞추는 방식은 두 가지로 해석된다.

| | A. 체험단원 보상에서 떼기 (현재 구조, 비율만 변경) | B. 고객사 결제액을 나누기 |
|---|---|---|
| 고객사 결제 | 보상 × 인원 (변화 없음) | **판매가** × 인원 (판매가를 고객사가 보는 가격으로) |
| 체험단원 수령 | 보상의 60% | 판매가의 60% |
| 플랫폼 | 보상의 40% | 판매가의 40% |
| 화면 문구 | "보상 30,000원 (수수료 40% 제외 후 18,000원 지급)" — 체험단원 체감이 나쁨 | 체험단원에게는 **받는 금액만** 표시(18,000원), 고객사에게는 판매가만 표시 |
| 평가 | 표시 문구가 신뢰를 떨어뜨림 | **권장.** 업계 관행(고객사 단가와 체험단원 지급액 분리)과 맞고, 비율을 숨길 필요도 없다 |

### 제안 (운영 설정값으로 관리)
1. 운영 설정 `payout.participantShare`(예: 0.6)를 `platform_settings`에 둔다(운영자 화면에서 변경, 기존 설정 편집기 재사용).
2. **미션 생성 시 비율을 미션에 복사**(`missions."participantShare"` 같은 컬럼) → 설정을 바꿔도 이미 등록된 미션의 약속 금액은 그대로.
3. 체험단원 지급액 = `floor(판매가 × 비율)`(원 단위 내림), 플랫폼 몫 = 나머지. 승인 시 이 값으로 정산 생성.
4. 상세 화면은 하드코딩 문구 대신 API가 주는 "체험단원 지급액"을 표시.

**결정 필요**: A/B 중 어느 구조인지, 비율(60:40 확정 여부), 원 단위 처리(내림 권장), 이미 등록된 미션에 적용할지(권장: 새 미션부터).

## 21. 정산(payouts) 흐름

### 현재 코드 (사실)
- **생성**: 콘텐츠가 승인되면 `payouts` 행이 `PENDING`으로 생긴다(승인은 검수 대기 상태에서만 가능해 중복 생성은 막혀 있음).
- **지급 방식**: 시스템 안에서 송금하지 않는다. 운영자가 정산 화면에서 "완료"를 누르면 상태만 `COMPLETED`가 된다 → 실제 송금은 시스템 밖(은행 이체)에서 하는 구조.
- **계좌 정보**: `payouts`에 `bankName`·`bankAccount`·`accountHolder` 컬럼은 있으나 **값을 쓰는 코드가 없다**. 체험단원이 계좌를 등록하는 화면도 없다 → 지금은 계좌를 카톡·문자 등 시스템 밖에서 받아야 한다(개인정보가 관리 범위 밖에 흩어짐). 저장되더라도 **암호화되지 않은 평문 컬럼**이다.
- **원천징수(3.3% 등)**: 처리 없음. 지급액 = 보상 − 수수료만 계산.
- 그 밖의 문제
  - 정산 상태 변경 API(`PATCH /operator/payouts/:id`)가 상태값을 검증하지 않는다(잘못된 값이면 500, `COMPLETED → PENDING` 같은 역행도 가능). 누가 언제 처리했는지 기록(감사 로그)이 없다.
  - 운영자 정산 목록이 최근 50건만 보여 준다.
  - `participant_profiles.totalEarned`(누적 수익)가 갱신되지 않는다.

### 세금 처리 방향 (세무사 확인 필요)
| 구분 | 적용 상황 | 원천징수 | 비고 |
|---|---|---|---|
| 사업소득 | 체험단 활동을 계속·반복적으로 하는 경우 | 3.3% (소득세 3% + 지방소득세 0.3%) | 지급명세서 제출 |
| 기타소득 | 일시적·우발적 활동 | 8.8% (필요경비 60% 의제 후 22%) | 기타소득금액 건별 5만 원 이하(지급액 약 12.5만 원 이하)는 과세최저한으로 원천징수 없음 |

- 어느 쪽이든 원천징수·지급명세서 제출을 하려면 **주민등록번호 수집**이 필요하다. 법령 근거(소득세법)가 있어 수집은 가능하지만, **암호화 저장이 법적 의무**이고 접근 권한·조회 기록 관리가 필요하다.
- 사업계획의 핵심 대상(한부모 가장)은 수입이 **한부모가족 지원·기초생활보장 소득 산정에 영향**을 줄 수 있다. 가입·정산 안내에 "소득 신고 대상일 수 있음"을 알리는 문구를 검토한다.

### 제안
1. **지급 수단 결정 전에는 계좌를 받지 않는 현재 상태를 유지**하되, 시스템 밖에서 받는 계좌 정보의 보관·파기 기준을 정한다.
2. 단계적 구현
   - 1단계(작음): 정산 상태 전이 검증(PENDING→SCHEDULED→COMPLETED/FAILED만), 처리자·시각 기록, 목록 페이지 넘김, 누적 수익 갱신.
   - 2단계: 체험단원 계좌 등록 화면 + **애플리케이션 단에서 암호화한 컬럼**(키는 서버 환경변수, 화면에는 끝 4자리만) + 개인정보처리방침 반영.
   - 3단계(세무 방침 확정 후): 원천징수 계산(사업/기타 구분, 과세최저한), 주민등록번호 암호화 수집, 월별 지급명세 내려받기(세무사 전달용).
   - 대안: 송금·원천징수를 대행하는 지급 서비스(PG사 지급대행, 프리랜서 정산 대행)를 쓰면 주민등록번호·계좌를 직접 보관하지 않아도 된다. 수수료와 비교해 결정.

**결정 필요**: 소득 구분(사업/기타) 방침, 직접 지급 vs 지급대행, 1단계 진행 여부.

## 22. 수익 구조 확장 (설계안)

### 22-1. 소상공인 구독 등급
| 등급 | 대상 | 포함 | 비고 |
|---|---|---|---|
| 무료 | 처음 써 보는 가게 | 미션 건별 결제, 기본 리포트(클릭 합계) | 지금 기능 그대로 |
| 베이직 (월정액) | 월 1~2회 미션 | 미션 등록 수수료 할인, 키워드 추천 상세(검색량·경쟁도), 기간별 리포트 | |
| 프로 (월정액) | 상시 홍보 | 미션 수 묶음, 체험단원 지정 재초대, 리포트 공유 링크 무제한·브랜드 표시 | |

데이터·구현 요지
- `client_subscriptions`(고객사, 등급, 시작·만료, 결제 상태) + 등급별 한도는 `platform_settings`(예: `plan.basic.monthlyMissions`)로 관리 → 등급 정책을 코드 배포 없이 조정.
- 한도 검사는 미션 생성·키워드 추천·공유 링크 생성 API에서 한 곳(`planLimits(clientId)`)으로.
- 월정액 결제는 토스페이먼츠 **자동결제(빌링)** 계약이 별도로 필요하다. 초기에는 월 단위 수동 결제(기존 결제창) + 만료 알림으로 시작 가능.

### 22-2. 지자체(B2G) 지역 성과 리포트
목적: 지역 상권 활성화·경력 단절 여성/한부모 일자리 사업의 성과 보고 자료.

| 지표 | 출처 | 비고 |
|---|---|---|
| 시·군·구별 참여 소상공인 수, 미션 수, 업종 분포 | missions, client_profiles | #17 지역 정규화가 전제 |
| 활동한 체험단원 수, 지급 보상 합계 | applications, payouts | |
| 콘텐츠 유입 클릭(고유 방문자) | click_daily | 기존 집계 재사용 |
| (선택) 참여자 중 한부모 가장 비율 | **별도 동의한 자기 신고 항목** | 민감할 수 있는 정보 → 수집 시 목적·보관 기간 별도 동의, 리포트에는 집계만 |

- 개인정보 보호: 셀(지역×기간)별 인원이 **5명 미만이면 숫자를 숨김**(작은 지역에서 개인 식별 방지). 개인 단위 자료는 제공하지 않는다.
- 전달: 기존 리포트 공유 링크(`report_share_links`, 만료·폐기 지원)를 지역 리포트용으로 확장 + PDF 내려받기.
- 계약 형태(용역/위탁)와 지표 정의는 지자체 담당 부서와 먼저 맞춘다.

**결정 필요**: 구독 등급·가격, B2G 리포트에 넣을 지표, 한부모 여부 자기 신고를 받을지.

## 23. 랜딩 문구: "지역 주민" 중심 → 핵심 대상(한부모 가장) 반영

### 현재 문구 (사실)
- 메타 설명: "소상공인과 지역 주민을 연결하는 하이퍼로컬 미션 매칭 플랫폼" (`frontend/src/app/layout.tsx`)
- 첫 화면: "지역 소상공인과 주민을 연결하는 맘브릿지", 참여자 카드 "지역 주민 (참여자) — 미션 수행 → 인증 제출 → 보상 수령" (`frontend/src/app/page.tsx`)
- 가입 화면 역할: "참여자 (지역 주민)" (`frontend/src/app/register/page.tsx`)

### 제안
원칙: 대상을 분명히 하되 **낙인을 주는 표현("취약", "어려운")은 쓰지 않고**, 한부모가 아니어도 참여할 수 있게 연다. 한부모 여부를 가입 조건이나 필수 입력으로 두지 않는다.

| 위치 | 안 1 (생활 밀착) | 안 2 (가치 강조) |
|---|---|---|
| 첫 화면 제목 | 아이 등원 후 2시간, 동네 가게를 돕고 수입도 만드세요 | 혼자 키우는 엄마·아빠의 시간에 맞춘 동네 일거리 |
| 부제 | 집 근처 가게 체험 후기로 보상을 받는 지역 미션 플랫폼 | 소상공인 홍보와 한부모 가장의 유연한 수입을 잇습니다 |
| 참여자 카드 | 엄마·아빠 체험단 — 원하는 시간에, 집 근처에서 | 체험단원 — 일정은 내가 정하고, 보상은 확인 후 바로 |
| 가입 역할 | 체험단원 (후기 작성) | 같음 |
| 고객사 카드 | 동네 가게 — 진짜 이웃의 후기로 알리기 | 같음 |

- 근거가 되는 약속(유연한 시간, 집 근처, 지급 시기)은 실제 운영과 맞아야 한다 — 지급 시기는 21번 결정 후 문구 확정.
- 권장: **안 1**(구체적 생활 장면이 대상에게 더 잘 닿고, 한부모가 아닌 사람도 배제하지 않음). 지자체·후원 기관용 소개(B2G)에는 안 2의 "한부모 가장" 표현을 명시.

**결정 필요**: 안 선택(또는 수정), 적용 범위(첫 화면·메타·가입 화면).
